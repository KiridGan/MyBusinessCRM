# Автоматическая наработка: установка и проверка

Обновление предназначено для полной схемы PR №3. Рабочая Supabase не использовалась при разработке; её фактические функции, ограничения, политики и данные должны быть проверены перед установкой. Наличие таблиц само по себе не доказывает, что прежние миграции установлены полностью.

## Как считается счётчик

Для каждой машины отдельно: **подтверждённая база + сумма текущих вкладов заказов − сумма вкладов в момент подтверждения базы**. Вклад пары `(заказ, машина)` хранится один раз и заменяется новым значением. Статус строго `Выполнен`; остальные статусы дают ноль. Повторное сохранение не добавляет часы. Удаление связи/заказа исключает вклад. Несколько машин считаются независимо. Для `hours` используются `work_hours`, для `km` — отдельное `work_distance`; часы аренды никогда не превращаются в километры.

Установка не включает автоучёт, не меняет старые показания, заказы, финансовые показатели или план ТО. Включение выполняется кнопкой отдельно для каждой машины после сверки фактического счётчика. Все связи с выполненными на этот момент заказами навсегда помечаются историческими, включая повторное добавление той же пары. Связи с незавершёнными заказами и новые пары учитываются при выполнении. Не вводите в них работу, уже включённую в подтверждённое начальное показание. Для переходящего заказа сначала сверяйте границу работы вручную.

Обычная ручная корректировка задаёт новую опорную точку и сохраняет историю. Например, после вклада 4 мч фактическое показание подтверждено как 300; изменение вклада 4 → 6 даст 302, отмена заказа даст 296. Это намеренный пересчёт разницы, а не удаление истории. Если результат стал бы отрицательным, вся операция отклоняется. Не исправляйте это изменением SQL-таблиц: проверьте фактическое показание и причину.

При физической **замене счётчика** используйте отдельный флажок в форме корректировки. Он начинает новый период: все существующие учтённые пары (также незавершённые) становятся историческими с нулевым вкладом; их прежнее состояние сохраняется в событии. Новые пары учитываются. Изменения старых пар не уменьшают новый счётчик. Прежние заказы и финансовая история сохраняются. Единицу измерения после начала истории менять нельзя.

`equipment.meter_value` остаётся исходным полем для совместимости. После начала истории текущее значение берётся из RPC `crm_meter_snapshot`, а не из этого столбца. Прямые изменения исходного поля блокируются; используйте «Внести фактические показания».

## Что добавляет SQL

- `equipment_order_links.work_distance`, `equipment.service_warning_threshold` (по умолчанию в приложении 10 мч / 100 км).
- `equipment_meter_accounts`: база, версия, включение; `equipment_meter_entries`: уникальные вклады/исторические исключения; `equipment_meter_events`: неизменяемый через клиент аудит с автором, временем, старым/новым значением, причиной, UUID запроса.
- Закрытая таблица `crm_meter_private.guards` сериализует операции по машине, в том числе до включения автоучёта.
- RPC снимка/подтверждения и атомарного удаления заказа, триггеры изменений статуса/связей, защита исходного счётчика; проверки конечных неотрицательных чисел.
- На новых публичных таблицах RLS и только SELECT своего владельца. Изменения доступны через проверяемую RPC. Внутренние функции недоступны клиентским ролям. Функции с повышенными правами имеют фиксированный `search_path` и явные проверки владельца. Удаление заказа работает с правами вызывающего, действующими RLS и финансовыми FK.

Существующие RLS, суммы, распределение выручки/расходов и финансовые триггеры не переписываются. При финансовой блокировке удаления откатывается вся операция, включая связи и наработку. UUID запроса предотвращает повтор ручной корректировки после сетевого сбоя; версия защищает от подтверждения устаревших показаний. Блокировки и запись guard предотвращают двойной учёт; при конфликте/взаимной блокировке транзакция откатывается, пользователь повторяет сохранение.

## Порядок внедрения для новичка

1. **Пока ничего не запускать в рабочей базе.** Открыть PR и проверить изменения. Сделать резервную копию базы средствами Supabase и убедиться, что известен способ её восстановления. Сохранить прежнюю версию сайта. Не помещать ключи или клиентские данные в GitHub/чат.
2. В отдельном тестовом проекте Supabase восстановить схему и обезличенные тестовые данные. Сначала выполнить `docs/preflight-equipment-usage.sql` через **SQL Editor → New query → Run**. Это только чтение. Ожидаются UUID, composite PK `(order_id,equipment_id)`, поля PR3, RLS и политики владельца. `order_budgets` в актуальной схеме находится в **crm_equipment_private**, не в public. Не создавать public.order_budgets вручную.
3. Если отсутствуют поля PR3 (`work_hours`, `hourly_rate`, поля автопарка, `order_contractors`), либо бюджетная схема/триггеры отличаются, остановиться и отдельно проверить предыдущий переход. Не запускать старые миграции повторно наугад. Этот PR не исправляет неполностью установленный PR2/PR3.
4. На тестовой базе открыть **весь** `supabase/migrations/20261102_equipment_usage.sql`, вставить в новую SQL-запись и выполнить целиком. В файле `BEGIN/COMMIT`: ошибка откатит установку. Скрипт одноразовый; повторный запуск намеренно останавливается. При неизвестной RLS-политике или структуре он требует проверки вместо молчаливого обхода. Не удалять конфликтующие объекты ради повторного запуска.
5. Развернуть ветку локально/в отдельном тестовом окружении (`python3 -m http.server 8080`) с URL и **publishable** ключом тестового проекта в принятом `config.js`. Не использовать secret/service_role. Проверить вход, заказы, подрядчиков, технику, сценарии ниже и два аккаунта.
6. После успешной проверки и отдельного подтверждения владельца назначить короткое окно обслуживания: закрыть CRM на всех устройствах, остановить редактирование. Повторить резервное копирование и read-only preflight на рабочей базе. Затем в SQL Editor выполнить **только новую миграцию целиком**, не переигрывая 20261028/20261031. При любой ошибке остановиться и сохранить текст ошибки без персональных данных. Таймаут блокировки означает, что операции ещё идут: не снимать защиту, повторить позже после проверки.
7. Проверить неизменность существующих заказов, показаний и сумм; новых meter accounts до подтверждений быть не должно. SQL можно установить до сайта: прежний интерфейс продолжает работать. Объединение PR и публикация GitHub Pages выполняются только после отдельного подтверждения. Сборки приложения нет — статические JS/HTML/CSS. Не требуется новый сервер.
8. После публикации войти, открыть машину, сверить счётчик и нажать **«Включить автоучёт»**, подтвердить начальную величину. Повторить отдельно для каждой машины. Старые устройства должны обновить страницу. Старый интерфейс не показывает расчётный счётчик; прямое изменение базового поля после активации будет отклонено.
9. Проверить два устройства: состояние обновляется после собственных действий, при возвращении в окно/сеть и опросом до 30 секунд. При сетевой ошибке не считать сохранение подтверждённым; повторить тем же запросом либо обновить форму и сверить значение. Автоматическое включение или перенос старых часов не выполняется.

До установки SQL новый сайт сохраняет прежние функции и показывает сообщение о недоступном автоучёте. После SQL откат сайта не отменяет учёт в БД. Не удалять новые таблицы/историю для отката; при проблеме остановить изменения и подготовить отдельную исправляющую миграцию.

## Проверка Rippa R10 и МКСМ-800

На тестовом проекте, без реальных клиентов:

1. Rippa: исходные 280 мч, ТО 300, порог предупреждения 20. МКСМ: исходные 100 мч. Включить учёт обеих. Существующий выполненный заказ при включении не должен изменить эти числа.
2. Создать новый незавершённый заказ; после сохранения открыть **«Техника и подрядчики»**. Добавить Rippa 4 ч и МКСМ 2 ч. До выполнения счётчики 280 и 100, подпись «ещё не начислена».
3. Выполнить заказ: 284 и 102; Rippa до ТО 16, предупреждение. Повторно сохранить: значения те же. Rippa 4 → 6: 286 и 102.
4. Отменить: 280 и 100; снова выполнить: 286 и 102. Убрать Rippa: 280; вернуть 6 ч: 286. Удаление заказа без финансовой истории исключает оба вклада; при связанной финансовой истории допустим защитный отказ без частичных изменений.
5. Открыть «Внести фактические показания», ввести причину. Проверить историю, прежнее/новое показание и автора. Открыть второй аккаунт: чужой техники, заказов, журнала и RPC-данных быть не должно.
6. Газель: 1000 км, часы аренды 4, пробег 40. Выполнение даёт 1040 км, не 1004. Повторное сохранение ничего не добавляет.
7. Следующее ТО меняется пользователем в редактировании техники; наработка его не переносит автоматически. Достижение 300 показывает «Пора выполнить ТО», превышение — «ТО просрочено».
