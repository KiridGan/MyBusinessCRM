# Запуск облачного раздела «Техника»

Изменения предназначены для отдельного Pull Request. Не объединяйте его с `main` до выполнения миграции и проверки в тестовой копии Supabase. `config.js` и существующие настройки авторизации не меняются. Новых Secret key/service_role в браузере нет.

## 1. Подготовка

1. Убедитесь, что существующие вход и облачные заказы работают. Используется тот же Supabase Auth и тот же клиент SDK, повторная авторизация не создаётся.
2. Сохраните резервную копию базы обычными средствами вашего Supabase-проекта. Для первого запуска используйте тестовый проект/ветку базы с копией схемы `orders` и двумя тестовыми пользователями.
3. Проверьте, что `public.orders.id` и `user_id` имеют тип UUID, а `expenses` — числовой тип. У `id` должна быть уникальность; у `user_id` — существующая изоляция через RLS. Скрипт не конвертирует старые типы или данные.
4. Если ключ ещё не настроен, добавьте только публичный Publishable key в `config.js` по [инструкции Supabase](./SUPABASE.md). Техника без входа не сохраняется локально и не подменяет облачный учёт. Не передавайте пароли/секретные ключи в чат и не записывайте их в репозиторий.

## 2. Выполнение миграции в Supabase

1. Откройте Supabase Dashboard **нужного проекта** → **SQL Editor** → **New query**.
2. Откройте файл `supabase/migrations/20261028_equipment.sql` в ветке Pull Request на GitHub. Скопируйте его целиком, от `begin;` до `commit;` включительно.
3. Вставьте скрипт в SQL Editor и выполните **Run** от имени владельца базы. Скрипт рассчитан на однократное применение; при любой ошибке вся транзакция откатывается. Если редактор оставил сессию в ошибочной транзакции, выполните `rollback;` перед исправлением и новым запуском.
4. Убедитесь, что созданы `equipment`, `equipment_expenses`, `equipment_order_links`. В **Table Editor** у всех трёх должен быть включён RLS.
5. Проверьте политики: для `authenticated` у каждой таблицы `USING (auth.uid() = user_id)` и `WITH CHECK (auth.uid() = user_id)`. Роль `anon` не получает права на эти таблицы. Нельзя добавлять permissive-политику с `true`.
6. Если таблицы/индекс уже существуют, не удаляйте их для повторного запуска. Это может быть уже применённая миграция либо конфликт с другой схемой: сравните структуру и журнал выполнения. Скрипт намеренно не маскирует несовместимость через `IF NOT EXISTS`.

Миграция **не удаляет и не переписывает** заказы, столбцы или существующие политики `orders`. Добавляется уникальный индекс `(id,user_id)` для безопасных составных внешних ключей и триггер проверки расходного бюджета заказа. Триггер запрещает снижать `orders.expenses` ниже суммы его детализаций в журнале. При этом сообщения в разделе заказов объясняют причину отказа. Новых машин и расходов скрипт не вставляет. Существующие строки и RLS-политики `orders` остаются без изменений. Служебные строки бюджета создаются только последующими операциями, не миграцией.

Третья таблица `equipment_order_links` хранит связь существующего заказа с машиной, не меняя текстовое поле `orders.equipment`. Составные внешние ключи не позволяют связать машину/заказ/расход разных пользователей. Один заказ можно связать с несколькими машинами. Первичный ключ связи — `(order_id, equipment_id)`; повтор той же пары запрещён, но другая машина допускается. Журнал ссылается на конкретную тройку `(order_id, equipment_id, user_id)`. Удаление связи удаляет только выбранную пару, а не все машины заказа. Выручка и расходы заказа делятся поровну между всеми связанными машинами; остаток копеек распределяется по стабильному порядку UUID. Сумма долей точно равна сумме заказа, без повторного учёта целиком у каждой машины.

## 3. Проверка перед публикацией

Разверните ветку PR на тестовом статическом HTTPS-хосте с тестовой конфигурацией Supabase либо запустите статический сервер локально на localhost. Все пути относительные, маршруты `#equipment` совместимы с GitHub Pages в `/MyBusinessCRM/`. Сборка не нужна. Не меняйте production `config.js` ради тестовой базы.

1. Войдите пользователем A → «Техника». До входа создание недоступно. После применения миграции кнопка «Обновить» должна загрузить пустой парк без ошибки.
2. Нажмите «Добавить технику». Проверьте шаблоны **Rippa R10**, **МКСМ-800**, **Газель Бизнес**: они только заполняют название/модель/тип/единицу счётчика. Год, реальные показания и инвентарный номер вводятся вручную. Нажатие шаблона или отмена ничего не сохраняют. Нажмите «Сохранить технику», когда данные проверены.
3. Измените модель/показания, обновите страницу. Проверьте сохранение и отсутствие дубля после повторной попытки при сетевом сбое.
4. В карточке укажите следующий порог ТО и/или дату. Дата не позже сегодняшней либо достигнутый счётчик дают «Пора выполнить ТО». За 7 дней, за 10 мч либо за 100 км появляется «Скоро плановое ТО». Действует первое достигнутое условие (дата **или** счётчик).
5. Создайте тестовый заказ, привяжите его в карточке техники. Выручка и расходы распределяются только по явной связи, не по похожему названию в старом текстовом поле. Привяжите тот же заказ ко второй машине: это разрешено. У каждой должна отображаться её доля; повтор той же пары запрещён. Снятие привязки второй машины не должно удалять первую или её журнал.
6. Добавьте в журнал ТО, ремонт, заправку и прочий расход. Проверьте дату, сумму с копейками, показания и описание. Измените и удалите запись; при отмене подтверждения она должна остаться.
7. Если сумма уже входит в `Расходы` заказа, выберите **«Уже учтено в расходах заказа»** и этот связанный заказ. Не вводите её повторно как отдельный расход. Суммарная детализация не может превышать `orders.expenses`; база проверяет это, а также запрещает уменьшать бюджет заказа ниже детализаций.
8. Проверьте период отчёта и расчёт по примеру ниже. Архивирование сохраняет журнал, связи и результат; фильтр «Архив» позволяет вернуть машину. Для безвозвратного удаления машины не должно быть связанных заказов/журнала. Для удаления заказа сначала уберите его привязку; запись журнала «Уже учтено» защищает её от удаления до ручной сверки. Ничего не удаляется каскадно.
9. Войдите тем же A на другом устройстве: данные должны появиться. Изменения подгружаются каждые 30 секунд при открытом разделе, при возврате во вкладку, восстановлении сети или кнопкой «Обновить». Выйдите и войдите B: машины, журнал и связи A не должны показываться. Проверьте прямые запросы с токеном B к известному ID машины/расхода A: SELECT пуст, UPDATE/DELETE не меняют строку; попытка вставить `user_id=A` или привязать машину A должна быть запрещена.
10. На смартфоне проверьте карточку, журнал и обе формы; горизонтальная прокрутка страницы не требуется. Отключите интернет при сохранении: форма должна остаться с введёнными данными и понятной ошибкой, без ложного сообщения об успехе.
11. Проверьте главную страницу, вход/выход и существующий полный сценарий заказа (создание, редактирование, поиск, статусы, удаление непривязанного заказа). Напоминания архива приостановлены; данные другого аккаунта очищаются при выходе.
12. После успешной проверки в тестовой базе выполните миграцию в рабочей базе, затем вручную объедините PR в `main` и дождитесь GitHub Pages. Этот PR автоматически не объединяется.

RLS следует проверять от имени анонимного клиента/обычных пользователей: SQL Editor владельца и service_role обходят RLS. На тестовой базе можно выполнить read-only проверку с подстановкой UUID тестового пользователя:

```sql
begin;
set local role authenticated;
select set_config('request.jwt.claim.sub', 'UUID_ПОЛЬЗОВАТЕЛЯ_B', true);
select set_config('request.jwt.claims', '{"sub":"UUID_ПОЛЬЗОВАТЕЛЯ_B","role":"authenticated"}', true);
select * from public.equipment;
select * from public.equipment_expenses;
select * from public.equipment_order_links;
rollback;
```

Вставьте действительный UUID; результат должен содержать только строки B. Для подтверждения запрета записей используйте тесты репозитория либо отдельные транзакции на тестовых данных, а не производственные заказы.

## Правила финансового учёта

- Период включительный, обе даты можно очистить для отчёта за всё время.
- **Выручка**: доля `amount` только привязанных заказов со статусом «Выполнен», по `order_date`.
- **Расходы заказов**: доля `expenses` всех привязанных заказов по `order_date`, включая отменённые/ещё не выполненные — фактически введённые расходы не исчезают из-за статуса.
- **Отдельные расходы**: журнал с `accounting_mode=additional`, по `expense_date`.
- **Всего расходы** = расходы заказов + отдельные расходы.
- **Операционная прибыль** = выручка − всего расходы.
- Журнал с `accounting_mode=in_order` — только детализация: он не прибавляется к расходам второй раз. Его дата может отличаться от даты заказа; для расчёта суммы заказа всё равно используется `order_date`. Не переносите один фактический расход между двумя источниками без сверки.

Пример: выполненный заказ на 1 000,10 ₽, его расходы 100,05 ₽; отдельная заправка 60,05 ₽; детализация ремонта 80 ₽ уже из тех 100,05 ₽. Выручка = 1 000,10 ₽, расходы = 160,10 ₽, прибыль = **840 ₽**, а не 760 ₽.

При добавлении отдельной суммы приложение не может определить по произвольному описанию, тот же ли это фактический расход, что уже был внесён в заказ. Поэтому источник учёта выбирается явно. Самостоятельно не записывайте одну сумму как `additional` и в `orders.expenses`: используйте вариант `in_order` для детализации. Техническое исключение повторного вычета и лимит детализаций проверяются кодом и базой.

## Защита от конкурентных изменений

В закрытой схеме `crm_equipment_private` находится `order_budgets` с `budget` и `allocated` по каждому заказу. К таблице нет доступа у `authenticated`, `anon` или `PUBLIC`, и она не используется как клиентский API. CHECK обеспечивает `0 <= allocated <= budget`.

Триггер INSERT/UPDATE/DELETE журнала резервирует/освобождает только дельту `in_order`. Смена заказа, суммы, источника учёта и удаление обновляют счётчики в той же транзакции. При переносе строки оба заказа блокируются в порядке UUID. Триггер UPDATE `orders.expenses` изменяет бюджет через UPSERT той же служебной строки. Даже первый расход, одновременно создающий счётчик, не может остаться незамеченным уменьшением бюджета.

Используется атомарный UPSERT, а не `SUM` из старого снимка. В READ COMMITTED запись после ожидания проверяет актуальную заблокированную версию. В REPEATABLE READ/SERIALIZABLE устаревшая конкурентная запись завершается ошибкой `40001`; возможный deadlock завершается `40P01`. При этих ошибках форма сохраняет поля и предлагает повторить операцию. Запись не повторяется автоматически, чтобы пользователь мог сверить изменения.

Два триггера бюджета — SECURITY DEFINER с фиксированным `search_path`, полностью квалифицированными именами объектов, проверкой владельца и отозванным EXECUTE у PUBLIC. Это нужно только для доступа к закрытому счётчику. Они не заменяют и не ослабляют RLS внешних INSERT/UPDATE/DELETE; составные FK дополнительно проверяют владельца. Прямой клиентский сброс счётчика и вызов функций запрещены. Администратор, отключающий триггеры/ограничения вручную, как и в любой базе, выходит за пределы этих гарантий.

Файл предназначен для первого запуска: предыдущая версия PR ещё не применялась. Если прежняя миграция уже выполнялась, не удаляйте таблицы и не запускайте этот CREATE-скрипт поверх них — потребуется отдельная добавочная миграция.

Для заказа на 100,01 ₽ с расходами 10,01 ₽ при двух машинах доли выручки составят 50,01/50,00 ₽, расходов 5,01/5,00 ₽. При изменении состава машин доли пересчитываются; общая сумма не меняется. Детализации `in_order` относятся к конкретной машине, но не переопределяют равное распределение общей суммы расходов заказа; в отчёте они показаны справочно.

## Эксплуатационные особенности

- Записи журнала с показаниями — история на дату события; они не меняют текущий счётчик машины автоматически. Текущие показания обновляются через «Редактировать технику».
- Единицу счётчика нельзя менять после появления журнала, чтобы старые моточасы не стали километрами. Исправление такой истории требует отдельной сверки данных.
- Напоминания отображаются внутри открытой CRM, это не push/SMS и не фоновый планировщик. После ТО установите новый порог/дату вручную.
- Архив не исключает машину из её финансовых расчётов; он скрывает её из списка действующей техники и приостанавливает напоминания.
- При сетевой ошибке новые облачные данные не сохраняются локально. Одновременное редактирование использует последнее подтверждённое сохранение.

## Автоматические проверки

```sh
npm ci
npx playwright install chromium
npm run check
npm test
# При установленном системном Chromium:
CHROMIUM_PATH=/usr/bin/chromium npm test
```

Тесты конкурентности автоматически запускают отдельный нативный PostgreSQL на localhost с временной базой и двумя независимыми подключениями. URL рабочей базы они не принимают; после теста кластер удаляется. Нужны обычный непривилегированный пользователь ОС и возможность запускать локальные процессы/сокеты; используйте обычный `npm ci`, чтобы выполнились скрипты подготовки бинарников. Эти тесты проверяют READ COMMITTED, REPEATABLE READ и SERIALIZABLE с контролируемым ожиданием блокировки. Дополнительные SQL-тесты запускают миграцию на PostgreSQL в памяти (PGlite), создают роли `authenticated`/`anon` и проверяют настоящие RLS/ограничения, архив и удаление, защиту истории и сохранность заказов. Это не подмена RLS в JavaScript. Браузерные тесты используют реальный SDK, но подставные HTTP-ответы, без ключей вашей базы. Сохранён полный набор регрессионных проверок авторизации и заказов. Реальная конфигурация вашего Supabase-проекта этими тестами не доказывается; её проверяют шаги выше.

Результаты выполненных проверок и матрица конкурентных сценариев: [EQUIPMENT-TEST-RESULTS.md](./EQUIPMENT-TEST-RESULTS.md).
