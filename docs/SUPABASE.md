# Подключение MyBusinessCRM к Supabase

## Что готово и что нужно настроить

Проект остаётся статическим сайтом для GitHub Pages: нет сервера, сборки и серверных переменных окружения. Главная страница сохранена. Заказы поддерживают два режима:

- Пустой Publishable key: прежнее хранение только в localStorage конкретного браузера, без синхронизации.
- Заполненный Publishable key: вход по email/паролю, заказы из `public.orders`, SDK восстанавливает и обновляет сессию. До входа облачные и старые локальные заказы не показываются. Ошибка облака НЕ переключает сайт незаметно на локальную запись.

Настоящий проект Supabase, схема и политики не проверены автоматически: Publishable key и тестовая учётная запись в эту среду не передавались. Тесты используют настоящую библиотеку SDK и подставной API, не производственную базу.

## Где добавить Publishable key

1. Откройте Supabase Dashboard → Project Settings → API Keys.
2. Скопируйте **Publishable key**, начинающийся с `sb_publishable_`.
3. В файле `config.js` замените только пустую строку `supabasePublishableKey: ''` на этот ключ. URL уже задан: `https://vrbbhmwwelfpgvvffsap.supabase.co`.
4. Сохраните конфигурацию в ветке с изменениями. После проверки и объединения в `main` GitHub Pages развернёт новую версию обычным способом.

Publishable key публичный по назначению: GitHub Pages отправит его браузеру. Его допустимо хранить в `config.js`; доступ к записям обеспечивает RLS и JWT вошедшего пользователя. Не присылайте пароли в чат. **Никогда не добавляйте в сайт Supabase Secret key, service_role или секрет подключения PostgreSQL.** Такие ключи нельзя сделать безопасными добавлением в JavaScript через GitHub Secrets. Код принимает только новый формат `sb_publishable_…`; старые JWT anon-ключи намеренно не принимаются.

Переменные GitHub Actions/Repository Variables сами по себе не попадают в статическую страницу. Если позже потребуется генерация `config.js` из CI, это отдельная настройка workflow; сгенерированный Publishable key всё равно будет виден посетителям. Не используйте GitHub Secrets для service_role в браузерной сборке.

## Authentication

Пользователь уже должен существовать в Supabase Authentication; регистрация новых аккаунтов на сайте не добавлена. Должны быть разрешены вход по email/паролю и, при необходимости, подтверждён email пользователя. Используются `signInWithPassword`, `getSession`, `onAuthStateChange`, `signOut({scope: 'local'})` официального SDK. Сессия сохраняется и обновляется SDK; пароль нигде не записывается приложением. Выход действует для этого браузера, не отключает другие устройства. На общем устройстве обязательно выходите: токен сессии хранится в localStorage браузера.

Для текущего входа по паролю редиректы не требуются. Site URL можно установить в `https://kiridgan.github.io/MyBusinessCRM/`; Redirect URLs понадобятся для отдельно добавляемых функций сброса пароля или OAuth.

## Соответствие полей

| Поле формы / старого localStorage | `public.orders` | Ожидаемый тип |
| --- | --- | --- |
| id | id | uuid, primary key / unique |
| вошедший пользователь | user_id | uuid, NOT NULL |
| — | created_at | timestamp/timestamptz, default now() |
| client | client_name | text, непустое имя |
| phone | phone | text |
| date | order_date | date |
| address | address | text |
| work | work_type | text |
| equipment | equipment | text |
| cost | amount | numeric, до двух знаков после запятой |
| expenses | expenses | numeric, до двух знаков после запятой |
| status | status | text либо enum с точными значениями ниже |
| comment | comment | text |

`amount` и `expenses`: от 0 до 1 000 000 000 000 включительно. При ограниченном `numeric(p,2)` проверьте, достаточно ли разрядов для ваших сумм. Прибыль вычисляется в интерфейсе в копейках, в базу не записывается. Для необязательных текстовых полей допускается NULL при чтении; приложение записывает строки. `amount`, `expenses` и `order_date` должны содержать корректные значения. `id` генерируется браузером как UUID. `created_at` создаёт база; отдельные запросы не передают его.

Статусы должны совпадать **буква в букву**: `Новая заявка`, `Согласован`, `В работе`, `Выполнен`, `Отменён` (с буквой «ё»). Несовпадение enum/CHECK, отсутствие поля или UUID вместо другого типа приведёт к понятной ошибке. Схема автоматически не изменяется.

Запустите [check-supabase.sql](./check-supabase.sql) в SQL Editor. Это только проверка чтением: она покажет столбцы, ограничения, RLS и права. Не пересоздавайте таблицу с существующими данными.

## Проверка RLS до публикации

RLS должен быть включён. Для роли `authenticated` нужны SQL-права SELECT, INSERT, UPDATE, DELETE и политики:

- SELECT: `USING (auth.uid() = user_id)`.
- INSERT: `WITH CHECK (auth.uid() = user_id)`.
- UPDATE: `USING (auth.uid() = user_id)` и `WITH CHECK (auth.uid() = user_id)`.
- DELETE: `USING (auth.uid() = user_id)`.

UPDATE должен запрещать и чтение чужой записи, и смену владельца на другого пользователя. SELECT нужен также для возврата сохранённых записей и переноса. Дополнительные permissive-политики с `true` могут расширить доступ; проверьте все политики, а не только четыре указанные. Не отключайте RLS для устранения ошибки. Клиент дополнительно фильтрует запросы по `user_id`, но это **не заменяет RLS**.

После добавления ключа проверьте в отдельном тестовом проекте/на тестовых пользователях: аноним не читает заказы; пользователь A создаёт и меняет только свои; пользователь B не читает, не меняет и не удаляет заказ A, даже при подстановке его ID; нельзя вставить `user_id` другого пользователя или сменить владельца через UPDATE. Одной проверки интерфейса для этого недостаточно. Автоматические тесты в репозитории проверяют обработку отказа RLS, но не доказывают корректность реальных политик.

## Как переносить старые заказы

1. Откройте CRM **по прежнему адресу GitHub Pages и в прежнем браузере**: localStorage привязан к origin (протоколу, домену и порту). В другом браузере/на другом домене старых данных не будет.
2. Войдите в нужный аккаунт и проверьте email в блоке переноса.
3. Нажмите «Скачать резервную копию» и убедитесь, что файл действительно сохранён. Файл содержит персональные данные заказчиков, храните его приватно. Токены и пароли в него не включаются.
4. Нажмите «Перенести в аккаунт» и подтвердите email и количество.
5. Сверьте результат и заказы на втором устройстве. Исходный ключ `MyBusinessCRM.orders.v1` не удаляется и не перезаписывается.

Импорт предварительно проверяет весь локальный список. Для каждой записи вычисляется стабильный UUID из проекта, пользователя и старого ID. Запись читается до вставки; вставка при конфликте не обновляет существующую запись, результат перечитывается для проверки. Повторная попытка после обрыва сети использует тот же ID. Журнал подтверждённого переноса хранится отдельно в этом браузере для каждого аккаунта. Он также предотвращает восстановление уже перенесённого и затем удалённого заказа при обычном повторном переносе.

Если запись с тем же ID в облаке отличается, импорт сообщает об этом и ничего не перезаписывает: локальный оригинал и резервная копия доступны для ручной сверки. При сбое частичный перенос не откатывается, его можно повторить без повторных вставок. При сбое записи журнала исходные данные остаются, существующие облачные ID обеспечивают повторяемость. Очистка журнала и повторный импорт из другого браузера могут восстановить ранее удалённую облачную запись из старого снимка; импортируйте резервные копии осознанно.

Одинаковые старые ID в разных копиях localStorage одного аккаунта не создают дублей. Разные ID при одинаковом содержимом считаются разными заказами: автоматическое объединение могло бы потерять настоящий повторный заказ. Импорт в другой аккаунт — отдельная копия, поэтому аккаунт всегда подтверждается явно.

Повреждённый JSON не перезаписывается и не импортируется. Кнопка резервной копии сохраняет исходную строку даже в этом случае. Формат копии: JSON с `format`, `source_key`, `raw`, `exported_at`; `raw` содержит прежний массив в виде строки. Автоматическое восстановление из файла не добавлено; сохранённый оригинал можно восстановить вручную после проверки.

## Синхронизация и ошибки

Список загружается после входа, после обновления страницы, при возврате во вкладку, восстановлении сети и каждые 30 секунд, пока раздел заказов открыт. Есть кнопка «Обновить». Записи читаются страницами по 500; список не ограничен первыми 1000 строками. Realtime/репликацию в Supabase включать не требуется.

Создание/изменение/удаление считается успешным только после подтверждения Supabase. Сбой оставляет форму открытой и не создаёт скрытых локальных заказов. Повтор создания после потерянного ответа использует тот же UUID. Нет офлайн-очереди: без сети новые облачные изменения не сохраняются. Автообновление списка не перезаписывает открытую форму. Если один заказ одновременно меняют на двух устройствах, побеждает последнее подтверждённое сохранение: поля версии/updated_at в предоставленной схеме нет.

При смене аккаунта/выходе список и форма очищаются, ответы предыдущего аккаунта игнорируются. На ошибки типов, RLS, истекшую сессию и сеть отображаются сообщения без токенов и паролей.

## GitHub Pages и проверки

Все ресурсы подключены относительными путями `./…`, поэтому работают в `/MyBusinessCRM/`. Маршрутизация использует `#orders`, перезапись серверных URL не нужна. Supabase SDK 2.49.8 включён в `vendor/`, внешнего CDN при работе сайта нет; лицензия рядом. Браузер должен поддерживать современный JavaScript, Web Crypto и `<dialog>`; используйте HTTPS GitHub Pages, не открытие через `file://` для облачного режима.

Сборка не нужна. Для разработки и тестов:

```sh
npm ci
npx playwright install chromium
npm run check
npm test
```

Если установлен системный Chromium: `CHROMIUM_PATH=/usr/bin/chromium npm test`. Тесты используют реальный включённый SDK, но полностью подменяют HTTP-ответы Auth и PostgREST. Реальная Supabase и ключи не нужны, производственные заказы не создаются.
