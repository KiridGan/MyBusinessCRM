# Где искать «Техника и подрядчики» после PR №3

Проверка выполнена 1 ноября 2026 по `main` = `9ba37b7` (слияние PR №3, head `03e77f0`). Рабочая Supabase не запрашивалась и не изменялась. Опубликованные файлы не изменялись.

## Основной вывод

В текущей реализации раздел находится **не в форме «Новый заказ» и не в форме редактирования**, а в карточке **уже сохранённого** заказа в списке «Заказы».

Порядок:

1. Заполнить и сохранить заказ.
2. Найти его карточку в списке заказов.
3. Нажать «Техника и подрядчики» в нижней части карточки.
4. В отдельном окне добавить свои машины/часы и подрядчиков.

Для проверки существующего внедрения можно просто найти ранее сохранённый заказ: создавать фиктивную запись в рабочей базе не нужно. Прокрутка формы «Новый заказ» не покажет этот раздел. Старое текстовое поле «Техника» в форме не является структурированной привязкой машин.

Причина: `equipment_order_links` и `order_contractors` ссылаются на сохранённую строку `orders` через FK. Создание заказа со всем участием одной операцией в PR №3 не реализовано; этот PR диагностики такой процесс не меняет.

## Подключение и обработчики

В `index.html` порядок корректен:

`config.js → vendor/supabase.js → cloud.js → orders.js → equipment-core.js → equipment.js → participation-core.js → order-participation.js`.

`orders.js` публикует общий `CRMRuntime` с Supabase-клиентом, пользователем и методами работы с отображением. `order-participation.js` регистрирует `crm-auth`, `crm-orders-rendered`, `crm-orders-changed`, изменения техники, возврат во вкладку/сеть и 30-секундный таймер. Начальная `session(runtime)` учитывает уже существующее состояние входа. Повторный Auth-клиент не создаётся.

`renderCards()` ищет только `#order-list [data-order-id]`; формы создания в этом селекторе нет. При входе должны успешно загрузиться `equipment`, `equipment_order_links` и `order_contractors`. Пустые таблицы допустимы. Пока загрузка неуспешна, кнопка сохранённого заказа отключена. Отказ SELECT-политики иногда даёт пустой список, а не HTTP-ошибку: по пустому парку нельзя однозначно диагностировать RLS.

## Какие таблицы нужны

Это соответствие **текстам миграций**, а не подтверждение наличия объектов в рабочем проекте.

| Объект | Предусмотрено PR №2 / `20261028_equipment.sql` | Дополнение PR №3 / `20261031_fleet_participation.sql` |
| --- | --- | --- |
| `public.orders` | Уже существовала ранее; добавляются составной индекс и проверка бюджета | Существующие столбцы/данные/RLS не переписываются |
| `public.equipment` | Создаётся собственный парк | Марка, госномер, стоимость покупки, ставка; «Неактивна»; архив вместо API-удаления |
| `public.equipment_expenses` | Создаётся журнал ТО/ремонтов/расходов | Использует обновлённый общий контроль бюджета |
| `public.equipment_order_links` | Создаётся связь заказа с несколькими машинами, PK `(order_id,equipment_id)` | Добавляются `work_hours`, `hourly_rate` |
| `crm_equipment_private.order_budgets` | Создаётся закрытый счётчик резерва | Резерв разделяют журнал и подрядчики; клиент его не читает |
| `public.order_contractors` | Не создавалась | Создаётся в PR №3: подрядчики, hourly/fixed, GENERATED amount, RLS и owner-FK |
| `auth.users`, `auth.uid()` | Уже предоставлены Supabase Auth | Не пересоздаются и не заменяются |

Именно новая `order_contractors` либо недостающие поля PR №3 могут блокировать участие, даже когда обычные заказы уже сохраняются. Одного Merge PR в GitHub недостаточно: GitHub Pages не выполняет SQL в Supabase. Базовая миграция тоже нужна — даже если планируется только привлечённая техника: клиент читает собственный парк/связи, а бюджет подрядчиков зависит от закрытого счётчика базы.

Полный раздел техники дополнительно читает `equipment_expenses`. Полноценное внедрение требует всей базовой схемы, обновлённых триггеров, корректных прав и RLS, не только одной таблицы подрядчиков.

- Прямое чтение публичных HTML/JS на `https://kiridgan.github.io/MyBusinessCRM/` **блокируется сетевым прокси среды (403)**. Это ограничение среды проверки, а не установленная ошибка вашего сайта. Фактические HTTP-статусы JS, MIME и кэш браузера пользователя не подтверждены.
- Состояние рабочей Supabase, применение SQL, её реальные RLS и ваши сессионные ошибки не проверялись. Пароли, реальные клиентские строки и токены для проверки не использовались.

Поэтому диагноз конкретного пользовательского симптома: **нет окна в новой форме — это предусмотренный порядок работы**, а не доказательство ошибки скрипта или неприменённой миграции. Если кнопки нет и в сохранённой карточке либо она отключена — нужен следующий шаг диагностики.

## Исправление в отдельном PR

В исходной `main` были недочёты обнаруживаемости, а не отсутствующая реализация участия:

1. Подсказка формы ссылалась на окно, не объясняя, что его открывают только после сохранения. Теперь порядок указан прямо.
2. Ошибка загрузки показывалась только внутри сохранённых карточек: при нуле заказов она была невидима. Добавлен общий статус и повтор загрузки над списком.
3. Ошибка/404 скрипта или зависимости могла оставлять пользователя без понятного сообщения. Добавлена проверка инициализации при загрузке страницы.
4. Загрузка через `select('*')` не проверяла новые поля на пустых таблицах. Для участия теперь явно запрашиваются необходимые колонки: неполная схема должна дать понятную ошибку до попытки сохранения.

Кнопка по-прежнему находится в сохранённой карточке. Новых таблиц, миграций и изменений бизнес-расчётов это исправление не добавляет. Для прежних потребителей `equipment-core.all()` сохранён default `select('*')`.

## Следующие действия для владельца

1. На существующем сайте войдите и посмотрите карточку уже сохранённого заказа в списке. Это нужное место кнопки, а не конец формы.
2. Если кнопка отсутствует, обновите страницу без кэша (не очищая localStorage). На компьютере в DevTools → Network проверьте `order-participation.js`, `participation-core.js`, `equipment-core.js`, `orders.js`: ожидается 200 и JavaScript, а не HTML/404. Посмотрите первую ошибку Console. Не пересылайте токены/пароли.
3. Если есть ошибка Supabase, запишите только код и имя таблицы/поля. `PGRST205`/`42P01` могут означать недоступную таблицу/описание схемы; `42703`/`PGRST204` — недостающее поле; `42501`/403 — права/доступ; `PGRST301`/401 — сессия входа. Сетевая ошибка сама по себе не доказывает отсутствие миграции.
4. Сначала согласуйте проверку **метаданных** целевого проекта. Подготовлен `docs/preflight-participation.sql`: только каталоги схемы, без заказов/клиентов/ключей; в рабочей базе этот файл не запускался. Он поможет установить фактическое состояние, а не угадать его по GitHub.
5. Только если подтверждено, что миграции отсутствуют, отдельно согласуйте их применение: сначала актуальный `20261028_equipment.sql`, затем `20261031_fleet_participation.sql`. Если база PR №2 уже установлена в поддерживаемой версии — первую повторно не выполнять. Если `order_contractors` уже есть — вторую целиком повторно не запускать: сравнить установленную версию и подготовить адресное обновление. При ошибке резерва/ключа не удалять данные и не обнулять счётчик.
6. Сначала проверьте SQL на тестовой копии и только после отдельного подтверждения — рабочий проект. Новый PR подсказок/диагностики также не объединяется и не публикуется автоматически.
