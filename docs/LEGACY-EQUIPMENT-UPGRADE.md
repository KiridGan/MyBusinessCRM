# Переход с уже существующей схемы техники без счётчика бюджета

Рабочая база не запрашивалась и не изменялась. Выводы о столбцах основаны на списке пользователя; типы, ограничения, данные и политики рабочего проекта пока не подтверждены.

## Сравнение с миграциями

| Объект | Что сообщено о рабочей базе | Что требуется текущему PR №3 |
| --- | --- | --- |
| `orders` | Все перечисленные поля совпадают с маппингом CRM | Столбцы остаются прежними; UUID id/user_id, numeric expenses, уникальный id, owner-RLS; составной индекс и триггер бюджета |
| `equipment` | Базовые поля до archived_at | Не хватает brand, registration_number, purchase_cost, hourly_rate; допускается статус «Неактивна» |
| `equipment_expenses` | По именам соответствует базовому журналу | Новые столбцы не нужны; нужны корректные owner-FK и атомарные триггеры |
| `equipment_order_links` | Только order_id/user_id/equipment_id/created_at | Не хватает work_hours, hourly_rate; нужен PK (order_id,equipment_id) и owner-FK |
| `order_contractors` | Отсутствует | Создаётся расширением PR №3 |
| `order_budgets` | По сообщению отсутствует | В коде это **crm_equipment_private.order_budgets**, не public.order_budgets |

По столбцам применена некоторая базовая версия учёта техники, но **точный номер/вариант миграции установить нельзя**: ключи, политики и триггеры в списке не видны. То, что Table Editor в `public` не показывает `order_budgets`, ещё не доказывает отсутствие таблицы в закрытой схеме.

Повторный `20261028_equipment.sql` натолкнётся на существующие таблицы/индексы. `20261031_fleet_participation.sql` ожидает частный счётчик, составной ключ и согласованный резерв уже установленной базы, поэтому при его отсутствии не подходит для самостоятельного запуска.

## Для чего нужен счётчик

Текущая реализация не использует public.order_budgets. В закрытой схеме хранится одна служебная строка на заказ: владелец, бюджет из orders.expenses и allocated — сумма детализаций in_order. AFTER-триггеры журнала/подрядчиков резервируют только фактическую дельту через UPSERT; триггер заказа синхронизирует бюджет. CHECK защищает 0 <= allocated <= budget при конкурирующих операциях. AFTER корректно обрабатывает ON CONFLICT, GENERATED amount и удаления. Клиент не имеет доступа к счётчику.

Счётчик **не является новой статьёй расходов**. Журнал/подрядчики in_order уже включены в orders.expenses и не вычитаются повторно; additional учитываются отдельно. Прибыль считается интерфейсом, не хранится в счётчике. Как бюджет защищён сейчас в рабочей базе, без определений её триггеров неизвестно: там может быть прежняя SUM-проверка либо другая реализация.

Отсутствие order_contractors непосредственно мешает загрузке окна участия. Отсутствующие поля equipment/links мешают сохранению расширенных карточек/часов; отсутствие закрытого счётчика мешает запуску обычной миграции PR №3 и работе её новых бюджетных триггеров.

## Подготовлен отдельный переход

`supabase/upgrades/20261101_upgrade_existing_equipment.sql` — **один альтернативный скрипт** для описанного состояния. Он выполняется вместо повторения двух исходных миграций, а не после них. Он лежит вне `migrations/`, чтобы автоматический runner не применил его к уже обновлённой базе.

Он:

1. Проверяет UUID/числовые типы, RLS, простые owner-политики, клиентские права, известные триггеры и отсутствие уже установленного счётчика/подрядчиков. Неизвестные политики не переписываются — скрипт останавливается. Поддерживаются обычные auth.uid()=user_id, обратная запись и распространённый SELECT-wrapper; более сложная логика требует отдельной проверки.
2. Проверяет владельцев, ссылки, дубли, суммы, источники расходов и соответствие детализаций бюджету. Превышение не исправляется увеличением orders.expenses или удалением расходов.
3. Поддерживает старый PK только order_id и составной PK. Преобразование PK сохраняет строки; при FK, зависящем от старого PK, останавливается без CASCADE. Неизвестные каскадные связи тоже требуют отдельного согласования.
4. Добавляет недостающие owner-ключи/FK. Новые ограничения проверяют все существующие записи, но не изменяют значения.
5. Создаёт закрытую схему/счётчик и **заполняет только новые служебные строки** из старых заказов/журнала. Например, 20 ₽ in_order + 7 ₽ additional дают allocated 20 ₽, не 27 ₽.
6. Устанавливает проверенные AFTER-триггеры, добавляет поля PR №3 и пустую order_contractors с RLS. Сохраняет существующие политики orders/equipment/expenses/links. У оборудования запрещается API-DELETE в пользу архива — как в PR №3.

Нет UPDATE/DELETE/TRUNCATE старых заказов, техники, журнала или связей. Нет автоматического создания машин/подрядчиков. Все изменения — в одной транзакции, есть таймауты. Скрипт рассчитан на однократное применение; при несовпадении состояния останавливается, а не пытается угадать версию.

## Что проверено

Тесты используют только придуманные данные и отдельные PostgreSQL/PGlite, не рабочую Supabase.

- Составной и старый одиночный PK связей: успешный переход, затем две машины одного заказа.
- Снимки всех прежних столбцов/строк заказов, техники, расходов, связей и RLS совпадают до/после. Права orders не меняются. Новые поля имеют начальные пустые/нулевые значения, не угадывают часы или стоимость покупки.
- Bootstrap корректно учитывает имеющийся in_order; резерв дополнительно разделяется с новыми подрядчиками. Уменьшение бюджета ниже детализаций запрещено.
- RLS-изоляция A/B и запрет API-удаления техники.
- 30 реальных сценариев двух подключений PostgreSQL 18.4 на READ COMMITTED / REPEATABLE READ / SERIALIZABLE запускаются именно поверх этого перехода.
- Превышение бюджета, небезопасная политика, выключенный RLS, чужой владелец, существующая закрытая схема и зависимый FK: атомарная остановка, исходные строки не исправляются, новые колонки/таблицы не остаются.

Команда: `npm run test:legacy-upgrade`. Старые файлы миграций, приложение, конфигурация и опубликованный сайт этим PR не меняются.

**Граница проверки:** совпадение столбцов не подтверждает типы/политики/данные рабочего проекта. Совместимость проверена с восстановленной схемой по сообщённым столбцам и поддерживаемыми вариантами ключей. Реальные RLS и суммы ещё нужно проверить. Предохранители не заменяют проверку метаданных и резервную копию.

## Что делать в Supabase SQL Editor — по шагам

Ни один из следующих шагов в рабочем Supabase автоматически не выполнен. Рабочие чтение метаданных и изменение схемы требуют отдельного подтверждения владельца.

### Шаг 1. Согласовать и выполнить только проверку

Откройте нужный проект → SQL Editor → New query. Сначала вставьте:

```sql
select
  to_regclass('public.order_budgets') as public_budget,
  to_regclass('crm_equipment_private.order_budgets') as private_budget,
  to_regclass('public.order_contractors') as contractors;
```

NULL означает, что объект по этому пути не найден. Если private_budget не NULL, **не запускайте новый переход**: нужно сверить уже установленную версию. Не создавайте вторую public.order_budgets.

Затем выполните полный `docs/legacy-equipment-precheck.sql`: он выводит структуру, ограничения, политики, права, определения известных функций и сводные количества проблем, без клиентских значений. В SQL Editor можно выделять отдельный SELECT и нажимать Run, чтобы видеть каждый результат; у сводных проверок ожидаются нули. Нужна проверка owner-RLS для всех четырёх таблиц, PK/FK, типов, прав TRUNCATE и известных триггеров. Не отправляйте клиентские записи, пароли или ключи. Если определения функций содержат случайно встроенные секреты, не пересылайте их.

### Шаг 2. Проверить точную схему вне рабочей базы

В тестовом проекте воспроизведите подтверждённую структуру и политики, заполните только придуманные заказы/машины/расходы. Сделайте проверенную резервную копию рабочей базы перед будущим изменением. Не копируйте клиентские данные в чат/тесты.

### Шаг 3. Применить один переход в тестовой базе

Откройте `supabase/upgrades/20261101_upgrade_existing_equipment.sql`, скопируйте **целиком**, от BEGIN до COMMIT. В SQL Editor тестового проекта нажмите Run. Не запускайте перед ним 20261028 или 20261031.

Если ошибка — выполните `ROLLBACK;` в той же сессии и остановитесь. Не отключайте RLS, не удаляйте таблицы, не обнуляйте резерв и не увеличивайте бюджет, чтобы «пройти проверку». Нужна адресная проверка причины. После успешного COMMIT новый ROLLBACK не отменит изменения.

### Шаг 4. Сверить результат

Проверьте появление brand/registration_number/purchase_cost/hourly_rate у equipment, work_hours/hourly_rate у equipment_order_links, order_contractors и закрытого счётчика. Заказы, исходные расходы и машины должны остаться прежними. Войдите тестовыми A и B, проверьте изоляцию, архив, две машины заказа, подрядчиков, изменение бюджета и отсутствие двойного вычета.

### Шаг 5. Отдельно подтвердить рабочий запуск

Только после успешной проверки точной схемы, резервной копии и явного подтверждения — короткая пауза редактирования и запуск **того же полного переходного файла** в согласованном рабочем проекте. При таймауте/ошибке остановиться. Затем проверить схему/итоги и окно «Техника и подрядчики» в карточке сохранённого заказа.

Merge PR и GitHub Pages — отдельные действия после подтверждения. Для уже опубликованной main PR №3 именно база остаётся отдельной стадией внедрения; GitHub Pages SQL не выполняет.
